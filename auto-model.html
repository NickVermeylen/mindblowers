Every team I've worked with has had the same conversation at some point: "Should we be using Claude or GPT for this?" Someone has a strong opinion. Someone else has different strong opinion. Nothing gets decided. Everyone keeps using whatever they were already using.

It's the wrong conversation. The real question isn't Claude vs OpenAI — it's which model for which task, and that answer changes across a single workflow. The good news is you only have to figure it out once. After that, you put it in config and forget about it.

Here's what the models actually do well, where they fall short, and the specific pattern I use to make model selection automatic.

The honest breakdown

What each family is actually good at

The marketing from both companies is useless for this decision. Benchmarks help, but only if you understand what they're measuring. Let me give you the practical version.

Claude — the long-context, instruction-following specialist

Claude's 200K context window isn't a marketing number. It changes what's possible. An entire large codebase — multiple service files, tests, configs, documentation — can fit in a single Claude context. You get coherent, whole-codebase reasoning without chunking, retrieval, or losing the thread.

In benchmark testing, Claude Sonnet 5 scored 82.1% on SWE-bench Verified — the first model to break the 80% barrier on real-world software engineering tasks. On SWE-bench Pro (harder, less gameable), it scores 63.2%, beating GPT-5.5 by 4.6 points. On long autonomous agent runs — seven hours, multi-file edits, sustained task continuity — Claude Opus demonstrates measurably better self-consistency and significantly fewer hallucinations than comparable OpenAI models.

The honest weaknesses: Claude is slower than GPT-4o on short-context tasks where latency matters. And for deeply mathematical reasoning problems — the kind of olympiad-level proofs where you want extended chain-of-thought — o3 is still ahead.

OpenAI — faster at short tasks, unmatched for hard math

GPT-4o is the fastest serious model available. For short, latency-sensitive tasks — quick completions, interactive suggestions, rapid iteration — it's noticeably snappier. If your workflow involves a human waiting for model responses in a tight loop, that matters.

The o-series (o3, o4-mini) is where OpenAI genuinely pulls ahead: hard reasoning problems. Algorithmic puzzles, mathematical proofs, optimization problems, complex constraint satisfaction — these are o3's home territory. The trade-off is speed and cost: o3 can take 30–60 seconds for a response, and that latency is structural, not a bug.

The context window is a real limitation — 128K tokens vs Claude's 200K. For small-to-medium codebases it doesn't matter. For large monorepos or wide architectural analysis, you start hitting it.

The mix that works

Stop picking one. Run both.

The developers I see spending the most are trying to find the single best model and use it for everything. The ones with the leanest bills use different models for different steps in the same workflow — deliberately, based on what each step actually requires.

Here's the workflow pattern that covers most coding agent scenarios:

orchestration & planning
Task understanding & plan
Claude Sonnet 5 or o4-mini
Decompose the task, identify unknowns, plan subtasks. Sonnet if it's a code problem; o4-mini if it requires algorithmic reasoning before any code is touched.
retrieval
Explore codebase, find relevant files
Claude Haiku 4.5
Read-only navigation. 200K context handles even large repos. 15× cheaper than Opus for identical file-search results. Zero tool-calling failures in benchmark testing.
implementation
Write & edit code
Claude Sonnet 5
Best SWE-bench score available. Instruction-following on large codebases is the defining strength. For pure math / algorithm design embedded in code: hand off to o4-mini for that subtask.
verification
Review, test generation, sanity check
Claude Haiku 4.5 or Sonnet 5
Haiku for mechanical checks (does this compile, are these tests structurally correct). Sonnet for semantic review (does this actually do the right thing).
hard reasoning (if needed)
Algorithm design, proof, optimisation
o3 or o4-mini
Reach for o3 only when the problem is genuinely hard reasoning — NP-hard scheduling, mathematical proofs, complex constraint satisfaction. For everything else in this slot, o4-mini costs 45% less and is nearly as capable.

This isn't theoretical. In a workflow with 20 subagent calls, routing the 12 navigation/search calls to Haiku and the 3 hard-reasoning calls to o4-mini can cut total subagent costs by 70–80% compared to running everything on Sonnet or Opus. The implementation calls stay on Sonnet, where they belong.

The config pattern

Bake the decision into your config. Stop making it per-session.

Here's the thing about model selection that nobody talks about: it's a decision that should be made once, not on every task. The model that's right for file navigation is always the model that's right for file navigation. It doesn't change session to session. So why are you choosing it manually each time?

Both Claude Code skills and agent config files accept a model field. Set it once. Every invocation of that skill or agent uses the right model automatically, with no thought required from you or the person running the session.

In Claude Code skill files

Any skill in .claude/skills/ or ~/.claude/skills/ can declare its model in frontmatter. The skill loads with that model pinned — the session model doesn't matter:

.claude/skills/explore/SKILL.md
# Read-only codebase navigation # Always runs on Haiku — never inherits session model
--- model: claude-haiku-4-5 effort: low description: Search the codebase, read files, find symbols and definitions. Read-only — never modify anything. ---
You are a read-only research agent. Use grep, file reads, and symbol search. Return findings as structured lists.
.claude/skills/reason/SKILL.md
# Hard reasoning — algorithm design, proofs # Routes to o4-mini via OpenAI-compatible endpoint
--- model: o4-mini effort: high description: Deep reasoning for algorithm design, complexity analysis, and hard optimisation problems. ---
Work through this step by step. Show your reasoning before the answer. Return: approach, complexity, code sketch.

Two skills — two models — zero per-session decisions

In agent definition files

Subagents defined in .claude/agents/ work the same way. The model field pins the model for every invocation of that agent, regardless of what the parent session is running on:

.claude/agents/implement.md
--- name: implement model: claude-sonnet-5 description: Writes and edits code. Handles large codebases. Do not use for pure math or file search. tools: - Read - Edit - Write - Bash ---
Implement the requested change. Follow existing patterns in the codebase. Do not refactor beyond the task scope.
.claude/agents/plan.md
--- name: plan model: o4-mini description: Task planning and decomposition. Breaks complex problems into concrete subtasks with clear scope. tools: - Read ---
Decompose this task into subtasks. Flag any ambiguities before planning. Output: numbered list, each with acceptance criteria and model hint.

Agent files pin the model — subagents never inherit by accident

The "model hint" in the plan agent's output is worth noting — it's a pattern where the planning step explicitly annotates each subtask with the model it should run on. If the plan says "Task 3: implement binary search tree — Sonnet" and "Task 4: prove worst-case complexity — o4-mini", the orchestrator routes accordingly without any human judgment at execution time.

The rule I use: If I'm writing a skill or agent and I can't immediately answer "which model should run this?", that's a sign the skill does too many things. Split it. Each agent should have exactly one kind of work, and that work should have an obvious model fit.

What about the session default?

On a Claude Code Max subscription, the default session model is Opus. Which means if you've defined zero subagent model overrides, every file read, every grep, every test run is being billed at Opus rates — $15/M input — for work that Haiku handles identically at $0.80/M.

The fix is three files: an explore agent set to Haiku, an implement agent set to Sonnet 5, and a plan agent set to whatever your planning work warrants. Opus stays in the session default for the conversations where it earns its rate — the complex discussions, the architectural decisions, the cases where you actually want the best model thinking about the problem.

Running everything on Opus is the AI equivalent of sending every company email via FedEx overnight because sometimes you send contracts. The routing exists for a reason.

The nuance

When the tidy mental model breaks down

I want to be honest about where this gets complicated, because the "use Haiku for navigation, Sonnet for coding, o3 for math" framework is a simplification.

The o-series latency is real. o3 takes 30–60 seconds to respond. If you've built a workflow where an o3 call is in the critical path — something the user is waiting on — that's a bad experience even if the answer is excellent. Use o4-mini instead for planning steps. Reserve o3 for genuinely hard, fully asynchronous reasoning jobs where the extra depth matters and latency doesn't.

Haiku's output limit bites on certain tasks. Haiku 4.5 has an 8,192-token output limit. GPT-4o mini caps at 16,384. If you're generating a large file, a long test suite, or multi-section documentation in a single call, Haiku might truncate. Either use Sonnet for that specific task or break the output into multiple calls.

OpenAI's ecosystem integrations are broader. If you're already deep in the OpenAI ecosystem — function calling conventions, fine-tuned models, Azure OpenAI Service, specific third-party tools that only support OpenAI — the switching cost is real. GPT-4o is an excellent model for most tasks, and the Claude-vs-OpenAI decision is much less important than "which model for which task within whatever you're using."

Benchmark gaming is a real problem. Both companies have been caught, or credibly accused, of optimising for benchmark scenarios. SWE-bench is more representative than most, but "82.1% on SWE-bench" is not the same as "82.1% of your real tasks done correctly." Test on your actual workload before committing to a model for production use.

The honest default: If you're building a net-new coding agent workflow today and don't have strong reasons to do otherwise — Claude Sonnet 5 for implementation, Claude Haiku 4.5 for retrieval, o4-mini for hard reasoning steps. Revisit when benchmarks shift, which they will.

The decision that doesn't need to be a decision.

You probably have a preferred model right now. It's probably whatever you were using when you first got serious about AI coding tools. That's fine — defaults exist for a reason. But the gap between "one model for everything" and "right model for each task type, baked into config" is where a meaningful chunk of your AI bill is hiding.

The config pattern takes an afternoon. Three agent files, three model declarations, done. After that, every session routes automatically: Haiku navigates, Sonnet builds, the reasoning agent reasons. You stop spending mental energy on model selection, and you stop accidentally billing Opus rates for grep.

The models will keep improving. The pattern stays the same: know what each step of your workflow actually requires, match the model to the requirement, put it in config, and move on to the work that actually matters.
