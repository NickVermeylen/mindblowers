The context window is not a landfill.

You're watching the progress bar on your monthly AI budget as your agent tries the same command for the fifth time. This time it'll work, you think.

A little while later, you're watching it generate a two-page design document for what should've been a three-line change. You close the terminal and implement it yourself.

If you've been using AI coding agents in the past year, this is your life. You've either accepted it as the cost of progress, or — like me — have been trying to stretch the token budget before someone notices the cloud bill.

Here's what actually works: configuration changes that are free and boring, and a handful of tools with real benchmark data. In rough order of impact.

Part 01 · Configuration

Fix your configuration first.

The uncomfortable truth: most token waste isn't a tooling problem. It's a configuration problem. You handed an agent a firehose and are surprised it's using it. Let's plug some holes before touching any libraries.

The AGENT.md file: your forgotten budget manager

Most people treat AGENT.md (or CLAUDE.md, AGENTS.md — pick your flavour) as a place to dump project context. That's only half right. It's also your first line of defence against runaway behaviour.

Stop loops before they compound. Hard iteration caps are the single biggest lever most people aren't pulling. If an agent hasn't resolved something after N attempts, it should halt — not heroically try a seventh variation of the same broken command. Add explicit rules like these:

# In your AGENT.md / CLAUDE.md
- Cap each debug loop at 2–3 attempts, then stop and report the blocker.
- Do NOT retry the same approach more than once.
  If something fails, form a new hypothesis first.
- If an assumption cannot be verified with available tools, STOP and ask.

This is unglamorous. It will not get a GitHub star. But it will save you more money than any compression library.

Budget guardrails at the agent level. Setting per-agent spend limits means a runaway loop hits a ceiling and dies quietly, rather than you discovering the damage on Monday morning. Tools like Airia have this built in; even a simple token counter with a hard stop in your orchestration layer goes a long way.

Preprocess your error logs. Dumping a 4,000-line stack trace into context and hoping the agent figures it out is like handing someone a bag of shredded documents and asking them to read the memo. Strip it first. Pass only:

  • The error type
  • The failing command
  • The last relevant stack frame

Not the whole dump. Not every timestamp. Not six repetitions of the same exception. Just the signal. Your agent will actually perform better — less noise to wade through — and your cost per call drops meaningfully.

Skills: teach once, reference forever

Instead of re-explaining project conventions in every conversation, encode them as reusable skills the agent loads selectively. Think of it as teaching your agent the codebase's rules once, rather than paying to repeat them on every invocation. Most agent frameworks support this natively.

Part 02 · Tools (with receipts)

Tools that actually help.

These fall into four categories: compressing what goes in, being smarter about what goes in, compressing what comes out, and full agent harnesses. Here's what the numbers actually look like.

Input compression: Headroom

Headroom trims input tokens before they reach the model — smart truncation and summarisation of conversation history and tool outputs. If you're building agents that accumulate long exchanges or chain tool results together, this is worth a look. Less in = less cost = faster responses.

Code search: Graphify and Semble

One of the most common token crimes: dumping entire files — or entire repositories — into context because you're not sure what's relevant. The fix isn't a bigger context window. It's smarter retrieval.

I ran a three-way A/B/C test: traditional grep+read, Graphify, and Semble, on the same set of codebase research tasks.

Semble wins on accuracy — it returns actual code snippets at the right line, giving the agent enough method-body detail to answer behavioral questions correctly while avoiding the full-file verbosity of traditional reads. Graphify is cheapest overall and wins when you need to map cross-file structure ("what depends on what", "which classes implement this interface"). In a separate two-way test focused on larger research tasks, Graphify consumed ~66k vs ~225k input tokens compared to traditional methods — roughly 3.4× fewer, translating to ~$0.27 vs ~$0.75 per session.

Traditional grep remains competitive when you already know exactly where to look. It used the fewest tool calls in the three-way test — because when the answer is one file away, you don't need a graph.

Recommended workflow: Semble for targeted behavioral questions → Graphify to map cross-file dependencies → traditional read only when you need the full file body. Don't SELECT * when you only need three columns.

Output compression: Caveman

Agents are, as a species, verbose. Ask one to rename a variable and it'll explain its reasoning in three paragraphs, write a changelog entry, and propose a refactor of the surrounding module. We love the enthusiasm. We do not love the bill.

Caveman is a Claude Code plugin that forces the model into compressed output mode — stripping responses down to the functional minimum. The results are honest: it depends entirely on the task type.

The lesson: Caveman isn't a silver bullet. It's a scalpel for the right kind of work — large-context summarisation where the model's verbosity is the actual bottleneck. Point it at a code review and you might make things worse. Point it at a documentation or summary task and it sings. Reported savings in specific setups have reached 75%.

Output compression: Ponytail

Ponytail takes a different philosophy: rather than compressing the output format, it teaches the agent to write less code in the first place — claiming a 54% reduction in generated code without breaking functionality. The idea is to aggressively discourage the model's habit of over-engineering. Instead of generating a helper utility, an abstraction layer, and a README for a three-line feature, it just does the thing.

On well-scoped, concrete tasks it's roughly a wash — both modes produce similar solutions, and normal mode can actually be more accurate (it finds the real method name; Ponytail sometimes guesses). Where Ponytail's philosophy has clear value is on vague, open-ended prompts. I tested "add a reporting system for sync stats":

This is where Ponytail's value is unambiguous. "Reporting system" is a scope magnet — it pulls in types, stores, endpoints, and interfaces by default. Ponytail short-circuited all of that by asking the real question: what does ops actually need to see? Three log lines. The caveat: on specific, concrete tasks, normal mode finds more accurate method names and often writes fewer lines. Ponytail pays off most when task scope is genuinely ambiguous and the risk of over-engineering is high.

Full agent harnesses: Pi

If you'd rather not assemble these pieces yourself — input compression here, loop guards there, output trimming somewhere else — full harnesses handle all of it. Pi is an agent orchestration layer that packages budget controls, smarter context management, and loop prevention into a single product. Benchmarks against vanilla Claude setups show meaningful cost improvements. It won't appeal to the "I want to understand exactly what's happening" crowd, but if you want to stop thinking about this and get back to building, it's worth evaluating.

Part 03 · The meta-lesson

The biggest lever isn't a tool.

The tools are real, and some of them work very well in the right context. But the biggest single lever — by a significant margin — is stopping bad loops early.

A single runaway debugging loop that spins fifteen iterations on a broken assumption doesn't just waste 15× the tokens on that loop. It fills your context window with noise, which makes subsequent reasoning worse, which causes more iterations, which fills the window further. It's a compounding disaster, and no compression library rescues you from it after the fact.

What actually works, in rough order of impact:

  • 01
    Hard iteration caps
    If the agent hasn't solved it in 2–3 attempts, force a new hypothesis or escalate. This alone is the biggest single bleed you can stop.
  • 02
    Structured error preprocessing
    Summarise logs into structured facts before they hit the context window. Error type + immediate context only — not the whole dump.
  • 03
    Surgical code retrieval
    Use Semble or Graphify instead of pasting files wholesale. Don't SELECT * when you need three columns.
  • 04
    Output compression on the right tasks
    Caveman Ultra for summarisation-heavy work. Ponytail for vague, scope-prone tasks where the model might otherwise over-engineer.
  • 05
    Full harnesses
    Pi and similar tools if you want loop prevention, context management, and budget controls packaged together.

The model isn't the problem. The cheapest model in the world will still burn through your budget if it's spinning in a loop, reading your entire codebase on every call, and writing four paragraphs to tell you it renamed a variable.

Your token budget is a resource, not a tax.

Tokens aren't infinite. Neither is your patience, or your cloud budget. Most of the waste is preventable — and the fixes range from free (configuration) to cheap (most of these tools).

None of this is as satisfying as installing a library and watching a metric improve. The biggest wins require discipline: structured instructions, loop guards, preprocessed inputs, surgical context. It's the AI equivalent of eating vegetables. Not glamorous — but your future self, the one looking at next month's invoice, will be grateful.

Now go put a loop cap in your AGENT.md. I'll wait.
